机场节点或 VPN 节点，在用户界面中通常指可选的一组连接参数或服务端位置。节点名是标签，实际入口、出口、协议、倍率与路径需要分别理解，不能由一个地区名称推导速度和网站可用性。

## 一次访问可能经过哪些位置

设备 → 服务入口 → 中间转发（可能存在）→ 服务出口 → 目标网站。简单连接中入口和出口可能在同一服务器，复杂服务则可能分开。这是概念图，不是某个收录品牌的实测拓扑。客户端本地监听端口又属于设备侧，不能与服务入口混为一谈。

## 节点列表里的字段怎样读

| 字段 | 能说明什么 | 仍不能单独证明什么 |
| --- | --- | --- |
| 名称与地区 | 提供方如何标记候选 | 真实物理位置、全部目标的地区判断 |
| 协议 | 所需客户端能力 | 当前网络连接一定成功 |
| 入口与端口 | 连接远端的参数 | 网站看见的最终出口 |
| 延迟 | 这次探测的表现 | 下载、会议与长期稳定 |
| 倍率 | 声明的计费系数 | 所有节点永久使用同一系数 |
| 在线状态 | 提供方监控状态 | 本地到节点的整条路径可用 |

## 地区与 IP 查询为什么不同

IP 地理库给出的是资料推断，目标网站还可能综合账号地区、语言、Cookie 或定位权限。MaxMind 说明地理定位存在精度和更新限制。先确认请求走了预期节点，再比较同一地址族的来源，不能只凭某页面地区推断线路全部物理位置。

## 节点数量怎样用于比较

多个条目可能共享入口、出口或上游，也可能因端口与协议生成不同名称。数量多不等于独立故障路径多。对普通用户应先列必要任务和接入，为每项保留少量已验证主备；无法确认独立性时写未知，不按条目数量评分。

## 一个三选一的假设例子

甲探测延迟低但上传失败；乙延迟稍高却能完成同一上传；丙只在另一接入测试过。这次可先选乙完成该任务，继续调查甲的失败，丙暂时不参加同条件比较。三者都是虚构候选，不能据此把某地区或品牌评为长期更优。

## 怎样记录一条自己的可用节点

填写日期、时区、接入网络、设备、客户端版本、档案日期、节点别名、协议和任务结果。失败写出阶段与恢复办法。Mullvad 的服务器资料公开类型、状态和所有权等字段，可以用于理解透明度，不代表其他服务也提供相同资料。

## 切换节点后的验收与维护

切换可能改变出口、路径与部分业务会话。重新建立目标连接，检查登录、上传和局域网，不只刷新查询 IP 页面。订阅更新后若节点改名，保留旧新对应与核对日期。分享记录前隐藏完整订阅、密钥、账号和不必要的地址。

## 常见问题

### 同一地区的节点可以直接互相代替吗？

未必。入口、协议、负载和目标路径可能不同，需用同一任务验证。

### 节点在线但连接不上，是假节点吗？

不能据此认定。先查监控覆盖、账户、配置与本地路径，保留可重复证据。
