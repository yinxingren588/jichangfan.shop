自定义 DNS 可能改变域名解析的去向、内部域名可见性和节点引导流程。先确认由系统、浏览器还是 VPN 接管解析，再决定在哪一层做一个可恢复的调整。

## 画出解析责任边界

系统 DNS、浏览器加密 DNS、客户端内置解析器和 VPN 下发解析器可能同时存在。某应用也可能自行解析。DNS 加密描述查询传输方式，不等于后续网页也经过 VPN；改变公共解析器也不会自动获得目标网站的访问资格。

## 先保存当前有效设置

记录修改前的解析器、客户端模式、所用网络服务和企业内网需求。单位域名可能只有内部 DNS 能解析。若客户端依赖先解析节点域名才能连接，再让这个查询依赖尚未建立的隧道，可能形成引导循环。

## 改动前需要回答的问题

| 问题 | 核对位置 |
| --- | --- |
| 节点域名由谁解析 | 客户端官方 DNS 流程 |
| 企业域名由谁解析 | 管理员的分域策略 |
| 浏览器是否绕开系统 | 浏览器安全 DNS 设置 |
| IPv6 查询怎样处理 | AAAA 与双栈策略 |

mihomo 有单独的节点解析器字段，其他产品未必同名。

## 一次只在一层做测试

先用官方推荐默认配置建立基线，再按相应文档改一个目标设置。分别访问公网域名、必要的内部域名和原来失败的目标，观察客户端日志。不要同时改路由器、系统与浏览器，避免出现无法归因的“恢复”。

## 一个引导依赖例子

假设远端 DNS 必须通过节点使用，而节点入口又需要该 DNS 解析才能找到。客户端若没有独立引导解析路径，就可能连接前卡住。应恢复官方给出的节点解析或默认方案，而非无限切换解析器 IP。示例说明依赖，不提供通用配置数值。

## 恢复与结果判定

恢复原设置并重新连接，必要时按产品说明处理缓存。只有应用完成原任务，才算本次修复有效。若变更后内网域名丢失，应恢复分域解析而非逐个写入 hosts；长期手工固定 IP 容易错过服务迁移。

## 补充核对细节

核对时将解析成功与返回地址的可用性分开：获得结果以后，地址族、证书与目标端口仍可能失败。企业搜索域和内部短名称也应保留独立样本，不能只用一个公网网站验证全部解析需求。改变前后的条件应写在同一张表中。

## 常见问题

### 使用加密 DNS 是否就没有泄漏？

不能这样推断。它只涉及一类查询传输，应用、路由和其他流量还需分别核对。

### 换 DNS 能解决所有握手超时吗？

不能。域名已正确解析后的端口、协议与远端故障不是 DNS 能直接修复的。
