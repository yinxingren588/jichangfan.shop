VPN 连接后的 IPv6 要检查“是否支持、如何路由、失败时如何处理”，而不只是看开关有没有打开。IPv4 成功不代表 IPv6 同样经过隧道，IPv6 不可用也不必然属于泄漏。

## 先读产品的双栈说明

确认当前客户端与服务端是同时承载 IPv4/IPv6、阻断 IPv6，还是只处理特定应用。系统代理、TUN 和完整 VPN 的范围不同。文档未明确时标注未知，不能因为系统仍有 IPv6 地址，就断言应用流量已经绕行。

## 分别建立连接前后的观察

使用同一设备和接入网络，分别记录 IPv4 与 IPv6 是否可达、所见来源和当前模式。没有原生 IPv6 的网络，无法据此验收客户端对 IPv6 的处理。测试页面还可能有缓存或只支持一种地址族，应先核对它的能力。

## 检查结果怎样分类

| 结果 | 合理解释与下一步 |
| --- | --- |
| IPv4 经过预期出口，IPv6 不可达 | 对照产品是否主动阻断 IPv6 |
| 两者均可达且来源符合说明 | 继续测试断线与重连行为 |
| IPv6 显示接入网络来源 | 核对是否在隧道范围及排除规则 |
| 仅某应用来源不同 | 查该应用代理、浏览器功能和规则 |

公网来源只是观察，不自动证明所有应用行为。

## 断线边界要单独验证

若产品声称断线保护覆盖双栈，应在低风险任务中按官方说明验收连接失效时的行为。不要在传输敏感资料时试验。测试后立即恢复原模式，并确认 IPv4、IPv6 和局域网任务都符合预期；不能靠一张在线截图覆盖整个生命周期。

## 一个双栈排错示例

假设宽带支持 IPv6，客户端文档写明阻断未进隧道的 IPv6，而测试页显示 IPv6 不可用。这个结果与说明可能一致，不能为了点亮绿色结果直接解除阻断。若换热点后测试页没有 IPv6，则需要标注该接入不具备同等测试条件。

## 发现路径不符怎样恢复

先停下相关敏感任务，恢复厂商推荐配置，核对排除路由和分流名单。仍不符时提交客户端版本、系统版本、地址族与脱敏日志。全系统关闭 IPv6 会影响其他服务，应优先用受支持的产品设置处理，而非把它当作通用修复。

## 常见问题

### 检测到 IPv6 地址就代表泄漏吗？

不代表。关键是实际请求是否在预期保护范围，以及来源是否符合产品说明。

### IPv4 和 IPv6 出口必须同一地区吗？

取决于服务设计；不一致需要核实，但单凭地区字段不能判定路由错误。
