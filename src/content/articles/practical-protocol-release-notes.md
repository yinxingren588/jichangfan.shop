客户端更新日志中，最需要关注的是影响现有配置、权限、DNS、路由与安全性的变化。新功能数量不是唯一重点，升级前要确认自己正在用的功能是否受影响。

## 先分清哪个组件在更新

图形界面、代理内核、驱动或系统扩展可能分别更新。界面版本不等于内核版本，自动更新订阅也不是软件升级。记录当前组合，才能找到真正适用的发布说明；不要把不同项目的同名版本号当作一回事。

## 按影响而非顺序阅读

| 变更类型 | 应核对的问题 |
| --- | --- |
| 破坏性变更 | 字段是否改名、默认值是否改变 |
| DNS 与路由 | 分流、IPv6、局域网是否受影响 |
| 权限与服务 | 是否需要重新授权或重启 |
| 安全修复 | 旧版是否仍适合继续使用 |
| 系统支持 | 当前系统与架构是否被支持 |

自己的核心功能对应哪一项，要做明确标记。

## 查清配置迁移说明

如果字段废弃，按官方给出的替代方案处理，不用简单删除所有警告。YAML 能解析只说明语法通过，内核可能不支持某功能。新默认值也可能改变行为，即使文件逐字未变；因此验收需要覆盖实际任务和退出后的网络。

## 一个默认行为改变例子

假设更新说明调整了某 DNS 字段的默认处理，而你的配置没有显式写该字段。升级后域名结果变化，差异可能来自新默认而非订阅被篡改。应核对发布说明与官方迁移办法，在副本中验证，不是同时更换 DNS、规则和节点。

## 升级前后做什么记录

升级前保存版本、可用档案与恢复渠道，升级后检查导入、核心任务、分流、局域网和重连。日志出现警告时保留全文和时间，脱敏后提交。不要为追求没有警告而关闭日志或降低证书与认证要求。

## 何时应该暂缓或回退

核心业务确有兼容阻碍时，先核对官方已知问题与受支持的恢复方案。涉及安全修复的旧版不能无限期保留；找不到可信旧包时也不能从不明镜像下载。记录临时措施与后续修复版本，再恢复当前维护版本。

## 常见问题

### 每次小更新都要重装吗？

通常按官方流程即可，只有说明要求时才处理额外组件，不必机械重装。

### 别人说更新稳定，自己的配置就不用检查吗？

仍需检查自己使用的系统、功能和格式；别人的环境不能替代你的验收。
